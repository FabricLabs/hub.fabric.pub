# Changelog
All notable changes to **hub.fabric.pub** (Fabric Hub) are documented here. RCs are coordinated with **`@fabric/core`** and **`@fabric/http`**.

## [Unreleased]
- **Semantic UI comes only from `@fabric/http`.** `npm run build:semantic` is `@fabric/http`'s `fabric-http-semantic`, and `npm run build` syncs through `@fabric/http/functions/semanticBuild`: both copy its prebuilt Fomantic UI 2.10.0-beta.129 files and fabric theme into `assets/` and import Twemoji. The unused vendored `libraries/semantic` (Fomantic 2.8.8), `semantic.json`, and `functions/fabricHttpSemantic.js` are removed. Customize with Fomantic site files under `semantic/site/` (only the ones you change) and `fomantic-ui` installed. Needs an `@fabric/http` with `functions/semanticBuild`.
- **Mailbox read proofs must name this Hub (breaking; needs the core with `MAILBOX_FETCH_PURPOSES`).** `GET /services/federations/messages` takes only a `DELEGATION_MAILBOX_FETCH` signed for one of the Hub's pinned origins with purpose `federation-mailbox`, and the delegation mailbox (`/services/delegation/mailbox`) only one for a pinned origin with purpose `delegation-mailbox`. A proof sent to another Hub, or for another use, can't be replayed here.
- **Tor onion service.** `settings.tor` / `FABRIC_TOR=1`, or the Tor box in first-time setup, serves the Hub's HTTP (onion port 80) and Fabric Peer port as a v3 onion service. By default the Hub runs its own `tor` (no SocksPort, no ControlPort, stopped with the Hub); `FABRIC_TOR_MODE=control` adds the service to a Tor you already run through its ControlPort instead. The onion key is the Hub's own (`stores/hub/tor/hidden_service`, Tor's file format), so the address is known before Tor starts and stays the same. Tor traffic comes in on a separate loopback listener whose connections are never treated as local, so onion visitors never get loopback trust. The onion origin is a pinned Passport origin. `GET /services/tor` shows the address only to the operator unless `TOR_ADVERTISE` is on.
- **`hub` command.** `npm i -g @fabric/hub` installs `hub` (alias `fabric-hub`): `hub setup` asks what the web onboarding asks (node name, Bitcoin preset or your own bitcoind, Lightning, LAN HTTP, Tor) and applies it through `POST /settings` when this data directory's Hub is running, else straight into its store, then saves the admin token to `~/.fabric/hub-admin-token`; `hub start`, `hub status`, `hub token [--save]`, and `hub tor [status|enable|disable]`. Data lives in `FABRIC_HUB_HOME` or `~/.fabric/hub` unless the working directory already holds `stores/hub`. `settings/local.js` is now in the npm package (the Hub needs it to start).
- **Payjoin: the Hub no longer pays its coins to addresses it does not own (security).** Anyone could open a deposit session for any address; with receiver contribution on (default on regtest), the Hub then added one of its coins to the output paying that address and signed it. Contributions now go only to addresses the Hub wallet owns (`getaddressinfo`, Hub Taproot templates), checked at session creation and again before signing, failing closed (`payjoin.requireOwnedReceiveAddress`). Anonymous sessions never get a Hub coin, and a payer can no longer turn the contribution on for its proposal. An original must also pay the session its full amount itself, so a Hub coin cannot make an underpaid invoice verify. Review: [docs/PAYJOIN.md](docs/PAYJOIN.md).
- **Payjoin resists UTXO probing and releases its coins.** One Hub coin per session; the same original gets the same answer; inputs already answered get `unavailable` in any session (`payjoin/seen-inputs.json`); at most `maxProposalsPerSession` (3) originals per session. After `fallbackAfterSeconds` (120) the Hub records which transaction appeared, broadcasts the sender's original when neither did, and unlocks the contributed coin. Coins from earlier Hub payjoins are never contributed (no snowballing). Originals must be `SIGHASH_ALL` (or Taproot default), must not spend a Hub coin, and stay within `MAX_MONEY` and 100 inputs / outputs.
- **Payjoin session and mailbox data are no longer public.** `GET /services/payjoin` lists recent sessions only for the operator; `GET /services/payjoin/sessions/:id`, `GetPayjoinSession`, and anonymous proposal answers return the payer view (no proposals, PSBTs, or contributed outpoints). Mailbox ids are 32 random bytes (they were derived from the creation time), `GET /services/payjoin/mailboxes` needs the admin token, and open mailboxes are capped (429).
- **BIP78 senders check more.** The browser and Hub senders refuse proposals that reorder our inputs, add receiver inputs of another script type or of our own coins; `pj=` endpoints must be https or .onion with no userinfo (`functions/payjoinEndpointPolicy.js`; plain http only off mainnet); the POST has a timeout, a response size cap, and no redirects.
- **Internal Payjoin (off by default).** `payjoin.internal.enable` / **`FABRIC_PAYJOIN_INTERNAL=1`**: the Hub wallet pays BIP21 `pj=` URIs through BIP78 (`sendpayment`, `POST /services/bitcoin/payments`, bridge sends) and `CreateDistributeInvoice` returns a `bip21Uri` with `pj=`. A failed proposal fails the send; nothing is broadcast. New: `GET|POST /services/payjoin/sends`, `GET /services/payjoin/sends/:id`, `POST /services/payjoin/sends/:id/cancel`, `POST /services/payjoin/sessions/:id/cancel`, `GET /services/payjoin/operations`, and RPC `CreatePayjoinSend`, `GetPayjoinSend`, `ListPayjoinSends`, `CancelPayjoinSend`, `CancelPayjoinSession`, `ListPayjoinOperations`. Other Hub operations are listed as stubs or not applicable (`functions/payjoinInternalOperations.js`); `/services/payjoin/v2/*` answers 501 until BIP77 OHTTP exists. WebSocket clients get `PayjoinUpdate` (id and status only).
- **WebRTC signals reach only their target.** `SendWebRTCSignal` delivers to the WebSocket that registered `toPeerId` and refuses a `fromPeerId` registered by another connection, instead of broadcasting SDP and ICE candidates (client IPs) to every client. `RegisterWebRTCPeer` refuses an id another live connection holds. Over HTTP the signal is refused. Needs `@fabric/http` that passes `connection` in method context; with an older one the Hub still broadcasts. The HTTP JSON-RPC route now calls `withContext` methods with a context, like the WebSocket path.
- **Payjoin session lists need the operator, and public network status drops browser details.** `ListPayjoinSessions` and `GET /services/payjoin/sessions` need the admin token (or a same-origin local call). Pushed network status, and `GetNetworkStatus` / `ListPeers` without the token, keep only the mesh fields of WebRTC peers' metadata (no user agent or refund pubkey). Bridge sends the admin token with `GetNetworkStatus`.
- **Federation mailbox reads need proof of key (breaking).** `GET /services/federations/messages` takes an `X-Fabric-Mailbox: fabric:<DELEGATION_MAILBOX_FETCH>` signed by the member key, which names the pubkey and `since`; each proof works once. A bare `?pubkey=` gets 401, so nobody can list another member's federation traffic.
- **Passport signs in to the Hub by its key, from any page (peer sessions, Passport v3).** Sign-in no longer depends on the page's origin being pinned (`FABRIC_HUB_PUBLIC_ORIGIN` / `FABRIC_HUB_PASSPORT_ORIGINS`): Passport connects to the Hub WebSocket itself, checks the Hub's identity key on a signed challenge, and keeps the session; calls are signed with a session key only Passport holds. `GET /sessions/peer` names the key, `GetPassportSession` answers who a call is from, and the pinned origins become the Hub's signed `homes`. Over HTTP, `POST /sessions/peer` runs the handshake and each request carries an `X-Fabric-Request` signed by the session key (bound to its method, path, body, and a one-time nonce); routes read either kind of session with `hubRequestSession`. `@fabric/hub/functions/hubPassport` is exported for apps built on the Hub. Pages fall back to the v2 cookie sign-in with an older Passport. Needs `@fabric/core` and `@fabric/http` with peer sessions (`functions/passportPeer`).
- **Heap snapshot files are named from fixed parts only.** `writeHeapSnapshot` takes the absolute `<store>/heap` directory the Hub resolves, refuses a relative one, and labels the file `signal`, `threshold`, or `snapshot` for any other reason (Codacy).
- **Purchased per-blob copies stay sealed in the browser.** Bridge drops a v2 delivery whose header lacks its Merkle root, payment hash, or blob count, or that has no `parts`, instead of keeping it pending forever. Opening a copy through the Hub needs the document key before the request and again when the answer arrives (the identity can lock in between); without it the copy stays pending to retry after unlock. The Hub-open button passes the operator token it was shown, with browser storage as the fallback.
- **The Peer page shows only its own payment confirmation.** Every `ConfirmInventoryHtlcPaymentResult` names its `settlementId`; the banner takes the result for the settlement it submitted, clears when the peer changes, and says "waiting for confirmation" only while the payment is pending.
- **A cut peer list is current, and as long as it can be.** `fitHubNetworkStatus` no longer lists `peers` in `truncated` (clients kept their old full list, so peer changes never arrived); it sets `peersPartial` with `peersTotal`. The list was cut before the large fields were dropped and never refilled, so local regtest Hubs sent `peers: []` and `deploy status` reported no Fabric peers on a full mesh. `chain` is now dropped with the heavy fields, the list keeps the most peers that fit, and each field dropped after it gives its room back to the list. `deploy status` doesn't report missing peers from a partial list.
- **The contract queue never counts an unwritten frame as stored.** A `writeFile` that returns `false` keeps the contract dirty for the next put or flush, and a stored document whose `entries` is not a list reads as empty instead of stopping the drain.
- **`migratewallet` is never forwarded to bitcoind** (it writes a wallet backup on the host).
- **The desktop shell does not start a second Hub while one survives SIGKILL.** `hubProcess` stays set until the child exits, and a restart stops there.
- **The bitcoind passthrough on `POST /services/bitcoin` needs the admin token for anything but chain reads.** Before, any caller could run any bitcoind method, including wallet sends.
  - Read-only chain and mempool methods (`getblockhash`, `getblock`, `getrawtransaction`, `estimatesmartfee`, …) stay public. Every other method needs `Authorization: Bearer <admin-token>` and otherwise gets 403.
  - Methods that touch files on the Hub host or stop the node (`dumpwallet`, `dumpprivkey`, `backupwallet`, `importwallet`, `loadwallet`, `stop`, …) are never forwarded.
  - The lists live in `functions/bitcoindRpcPolicy.js`. `verifymessage` is still answered locally.
- **A page on another site no longer gets loopback privileges on `POST /services/rpc`.** Its request reached 127.0.0.1 like any local one, so it could ingest a local file with `CreateDocument { filePath }` and read it back. Loopback trust now also requires the request not to come from another origin (`Origin` other than the Hub, or `Sec-Fetch-Site: cross-site` / `same-site`), the same check `config.local.js` already used. Scripts and the Hub's own page are unaffected.
- **Wallet, peer and worker JSON-RPC methods are operator-only.** `AddPeer`, `RemovePeer`, `SetPeerNickname`, `getUnusedAddress`, `GetAddressBalance`, `CreatePayjoinDeposit`, `DrainContractMessageQueue`, `GetNodeWealthSummary` and `ListWorkerQueue` need an `adminToken` (in any object param) or a same-origin loopback HTTP call (`Hub#_rpcCallerIsOperator`). Others get `adminToken required`. `GetBitcoinStatus` drops the wallet balance, recent transactions and Beacon for them, as `GET /services/bitcoin` already did.
  - The Hub page sends the token with peer add / remove / nickname, and the Admin page with its worker calls. Node scripts and tests calling `127.0.0.1` keep working without one.
  - Payjoin session lists (`ListPayjoinSessions`, `GET /services/payjoin/sessions`) are still public; the payments UI reads them without the token.
- **Other sites can't open the Hub WebSocket over loopback.** An upgrade on a loopback socket needs a rebind-safe `Host` and the Hub's own `Origin`, no `Origin` (scripts), a Passport extension origin (`FABRIC_PASSPORT_EXTENSION_IDS`, any `moz-extension://`), or an origin in the new **`FABRIC_HUB_WS_ORIGINS`** list. LAN and proxied upgrades are unchanged, so CDN builds still join public Hubs. Needs `@fabric/http` with the `websocket.verifyOrigin` hook; an older `@fabric/http` ignores it.
- **Review fixes.**
  - A contract-message frame is written to its queue document as soon as it is enqueued; only delivery marks are coalesced (`CONTRACT_MESSAGE_QUEUE_FLUSH_MS`), so a crash can resend a frame but not lose one.
  - A per-blob file that arrives without every blob's sealed part is dropped instead of replacing a sealed copy that is waiting for its key.
  - A network status that had to halve its peer list lists `peers` in `truncated`, so clients keep their full list.
  - The desktop shell waits for a killed Hub to exit (SIGTERM, then SIGKILL) before it starts another on the same port and data folder.
  - The document page ignores a market-agent answer that arrives after you moved to another document.
  - Heap snapshots live in `functions/hubHeapTelemetry` (`functions/hubHeapSnapshot` is gone). Delegation imports `@fabric/core/types/delegation` and `@fabric/http/functions/fabricDelegationHttp` (rendezvous and mailbox).
- **Paid documents are delivered after a confirmation, instances keep their playnet sessions, and browsers open per-blob purchases through the Hub.** These are fixes for rehearsal findings.
  - A seller now hands over a document only once the payment has `documents.minPaymentConfirmations` confirmations (`FABRIC_DOCUMENT_MIN_CONFIRMATIONS`, default 1; 0 restores mempool delivery). Until then an unconfirmed payment, which could still be replaced, opens nothing.
  - `ConfirmInventoryHtlcPayment` records the funding and returns `{ status: 'pending', confirmations, required, retryWithSameTxid }`. The payment is checked again on every call. The refund-lock margin still applies.
  - Each new block (and the minute timer) runs `_deliverConfirmedHtlcPayments`, so the buyer gets the file and key without confirming again. Concurrent confirms for one settlement send once. A recorded payment that has left the mempool is looked for only in the blocks since its last check (`paymentScannedHeight`), so a replaced payment doesn't cost a 10,000-block scan on every block.
  - `ClaimPurchase` answers `pending` until the payment confirms, and the same claim token works afterwards.
  - `scripts/documents.js buy` keeps polling through `pending` and prints the count. PeerView now shows confirm results, including the wait.
  - New Hub setting `redialPeers`: peers the Hub never dials at boot but redials on the `peerRedialMs` tick, alongside `peers`.
  - The first redial tick lands at a random point within the interval, so instances started together don't handshake with a public Hub at once.
  - Hostname entries are matched against open sessions by their resolved addresses, cached for 5 minutes, because core keys a live session by IP.
  - `deploy` gives non-seed instances the remote Hubs as `redialPeers` (through `buildFragment`). Before, those instances lost them for good after a dropped session or a restart outside deploy.
  - The browser Bridge recognizes v2 (`perBlob`) deliveries. It stores them pending, keeping `htlcFileV1` and `parts`, instead of saving the ciphertext as if it were the document.
  - The browser opens a v2 copy through its own Hub (`openPurchasedDocumentViaHub` → `OpenPurchasedDocument`, admin token, optional claim preimage). DocumentView offers "Open with this Hub", or explains that the copy opens on the Hub that bought it.
  - Unlocking a v1 copy in the browser now clears its pending state; before, the stored record kept `htlcPendingDecrypt`.
- **Bought per-blob documents open, and the admin token re-signs on deploy.** A priced document is sealed blob by blob, but delivery encrypted that ciphertext again under the batch preimage `S` with a v1 header and no blob keys, so the buyer held bytes nothing could open (`OpenPurchasedDocument` failed even with the right key). The sale now sends the stored ciphertext as-is under a v2 `htlcFileV1` header (`{ v: 2, scheme, perBlob: true, merkleRootHex, blobTotal, paymentHashHex }`), and each `P2P_FILE_SEND` frame carries its blob's `sealedPart` (`iv`, `keyHashHex`, the blob key wrapped under `S`). Sealed blobs are exactly as large as share blobs, so blob `i` rides on frame `i` and the entries never outgrow a frame. The buyer collects them while the transfer arrives (`documentFileShare.createSealedPartCollector`, a few transfers for 15 minutes), keeps `parts` and a private `documents/<id>.batches`, and on the key reveal or a claim preimage marks the copy `encryption.perBlob`. `OpenPurchasedDocument` then opens it with `S`, and a resale sends the same bytes and wraps. The reveal no longer carries wraps. `deploy --local start` re-signs a saved admin token that the instance's current identity key no longer verifies (`refreshAdminToken`), since setup issues only one.
- **xpub queries take their watch list from the body.** `POST /services/bitcoin/xpub`, `…/xpub/utxos`, and `…/xpub/transactions` (and the client-wallet `wallets/:walletId` summary) read `addresses` (comma string or array) and `limit` from the JSON body before the query, so a client can keep its xpub and addresses out of URLs and logs entirely. Passport now posts them.
- **The contract message queue no longer stalls the Hub.** Every queued `CONTRACT_MESSAGE` and every delivery mark re-read, re-hashed, and rewrote the contract's whole queue file (indented JSON, synchronously), and a peer connecting drained up to 64 frames per contract, one rewrite each. With 512 frames near the 32 KiB limit a file reached about 30 MiB, and peers reconnecting every minute kept the event loop busy until HTTP and the Fabric listener stopped answering (2026-10-21, 2026-11-02). The Hub now keeps each queue in memory after the first read, writes compact JSON at most once a second per contract (and on stop), and keeps at most 4 MiB of frames per contract, dropping delivered ones first; a larger file shrinks on its first read.
- **Queued contract messages go to a peer's mailbox, not its connection.** Delivery was tracked per `host:port`, so a peer reconnecting from a new ephemeral port got every queued frame again, and a peer on two connections got each one twice. Each peer now has one mailbox, keyed by its Fabric id (`fabric:<id>`); its `host:port` connections only carry the frames, so a reconnect sends nothing it already has. A connection is drained once its identity is known: on core's new `peer:session` event, or for an older core by checking every 250 ms for up to 10 s after connect. A connection whose identity never becomes known gets nothing. A frame is no longer sent back to the peer it came from. Address marks from before mailboxes are dropped on first read, and each frame keeps its 64 newest mailbox marks. `DrainContractMessageQueue` takes a Fabric id (`peerId`) as well as an `address`, and `ListContractMessageQueue`'s `peerKey` may be either.
- **Network status pushes fit one frame.** `GetNetworkStatus` and the WebSocket status push dropped only the heavy fields, so a status still over the frame limit (424 KB on hub.fabric.pub) failed on every peer change. After those fields, the Hub now keeps the first `peers` (with `peersTotal`) and then drops the largest remaining fields (listed in `truncated`), keeping the Hub's identity, setup, and listener. Pushes from a burst of connects and closes go out once a second.
- **Market budget and channels need the admin token; bounties need a known tip.** `GET /services/market/agent` and `GET /services/market/channels` served the budget agent's spending and the payment channels to anyone; they now answer 403 without the admin token, like the writes. `Hub.stop()` stops the Market service, so the budget agent halts and telemetry is saved before Bitcoin and the filesystem shut down. A bounty bond without `refundAfterHeight` counted the refund height from the cached chain height, which is 0 before the first block arrives, so the publisher could take the bounty back at once; the Hub now asks Bitcoin for the block count and refuses the bond while the tip is unknown. `ChallengeService#commitmentFor` uses only commitments naming this Hub as publisher (x-only or compressed), since fraud proofs bind a challenge to its commitment's publisher.
- **Linked signers replace device links; the Hub signs by rule.** The Hub is now a participant in `@fabric/core` delegation (`docs/DELEGATION.md`): `services/delegation.js` holds its own key and message store (`stores/hub/delegation/`), and `functions/fabricDelegateHub.js` mounts the `@fabric/http` pairing rendezvous (`/delegations`), the request mailbox, and the loopback delegate for Passport. Pairing shows a six-digit code in a native dialog; the Hub's grant covers `identity`, `passport`, and `federation` and discloses its cosigner key, so Passport can build a shared wallet with it. Requests are decided by **signing rules** (`functions/signerRules.js`, `/settings/signing`, `stores/hub/signer-rules.json`): sign or decline by scope, requester, site, federation, network, amount, destination, sats per day, and requests per hour. They fail closed — a decline wins, a broken rule set signs nothing on its own, and a withdrawal needs a rule with `maxAmountSats` (never above `maxWithdrawalSats`). Anything no rule settles waits for the operator: the desktop dialog, and Sign / Decline under Notifications with a badge in the top bar (`DelegationRequestsPanel`, `DelegationRequestWatcher`). Federation invites and withdrawals are answered as the cosigner (`FederationsService#answerDelegated`), and federation frames arriving from the mesh go through the same rules. Admin routes (Bearer): `GET /services/delegation/requests`, `POST …/requests/:hash/sign|decline`, `GET|PUT …/rules`, `GET …/decisions`, `GET …/signers`, `POST …/grants/:hash/revoke`; Security lists linked signers with Revoke. **Removed:** device-link (`functions/fabricDeviceLink*`, `fabricLinkedDevices`), identity clusters and `IdentityCrossSign` (`functions/identityCluster*`, `identityCrossSign*`), the `/services/fabric/{identity,sign,link}` local signer (`functions/fabricLocalSignerHub`), and their package exports; `fabric://link` is ignored. Pair again from Passport; nothing carries over ([PASSPORT_V2_CUTOVER.md](docs/PASSPORT_V2_CUTOVER.md) step 5). The Identity page finds Passport with `probePassport` (`PASSPORT_HELLO`) instead of reading the `<html>` marker.
- **No priced document sales on mainnet yet.** The current sale reveals a document's content key as the HTLC preimage, which isn't safe on mainnet. On a mainnet Hub, listing a document at a price (`PublishDocument`, `SetDocumentPrice`, market republish and seeding), invoices and claims (`CreatePurchaseInvoice`, `ClaimPurchase`), HTLC quotes on inventory replies, paying a quote (`PayInventoryHtlc`), and building a mainnet offer escrow (`BuildDocumentOfferEscrow`) are refused. Claiming, refunding, and opening documents already bought still work. The new sale protocol lifts this.
- **Security: document reads, writes, and listings are checked.** `GetDocument` took a document id as a path, so `../` read any file under the Hub store, including the content keys of every document for sale; `CreateDocument` wrote to a client-chosen path, and named a document by a `sha256` the client supplied, so anyone could replace a listing with other content. Document ids are now `[A-Za-z0-9_-]{1,128}`; a created document is named by the hash of its content (a different `sha256` is refused), and creating content the Hub already holds returns the existing document unchanged. Without the admin token, `GetDocument` no longer serves the ciphertext of a sealed or bought document (`contentWithheld: true`): with one paid claim on chain revealing the key, that ciphertext was readable by anyone. Setting a price, re-listing, and publishing a sealed document (`PublishDocument`, `SetDocumentPrice`) need the admin token, as do `SendPeerFile` and `EditDocument` of a sealed or bought document. A file pushed by a peer no longer overwrites a document this Hub sells or holds the key for. `components/Bridge.js` sends the browser's admin token with a priced publish; `scripts/verify-document-purchase-e2e.js` and `scripts/capture-user-flows.js` do too.
- **Paid prices start at 716 sats, and a small sale can be claimed.** A price below core `HTLC_MINIMUM_SATS` (716) is refused, and the seller's claim fee defaults to what the claim needs (at least `HTLC_CLAIM_VBYTES`, at most 1000 sats, leaving at least dust); a 500-sat sale used to be unclaimable at the fixed 1000-sat fee.
- **Large catalogs page; offers key by seller; unpublished files stay private.** A Hub with about 22 priced documents sent an inventory reply (one HTLC quote each) over the 32,976-byte frame limit, so peers dropped it and nobody could buy from it. Replies now go out as pages sharing an `inventoryId` (core `paginateInventoryItems`). The Document Market keys a seller's offers by the Fabric id its connection authenticated (`peerId`), so a seller that reconnects replaces its rows instead of listing twice, and a reply without quotes (a resync) keeps a quote the buyer already holds. The inventory lists only published documents: it used to name every file the Hub held, private and bought ones included, to any peer that asked.
- **Sellers claim their sales, direct purchases belong to the payer, and a busy peer can't push out other buyers' quotes.** A delivered inventory sale stayed unclaimed until the operator ran `ClaimInventoryHtlcOnChain`, and an unclaimed HTLC is refundable to the buyer after its lock. The Hub now claims as soon as it delivers and retries every minute (`claimAttempts`, `claimError`), giving up after 20 tries or on a coin already spent (`claimAbandoned`); a second claim answers "Already claimed." `CreatePurchaseInvoice` kept one invoice per document, so a second buyer's invoice replaced the first and the first buyer's payment could no longer be claimed, and anyone holding the public txid could claim the document. It also took the buyer's amount as the price. Each invoice now has an `invoiceId` and a `claimToken` returned only to the caller; `ClaimPurchase` needs the token, the amount is at least the listed price, and invoices persist in `bitcoin/purchase-invoices.json` (30 days, at most 5,000) so a restart doesn't strand a payment. `components/Bridge.js` keeps the token for the claim. HTLC quotes were evicted oldest first across all buyers, so one peer asking for inventory over and over pushed out every other buyer's quote; eviction now takes unpaid quotes from whoever holds the most (at most 512 per requester, keyed by the peer id its session authenticated or the relay it came through), and claimed sales go only after every unpaid quote.
- **Invoice and storage limits a peer can't run past.** A full invoice book dropped the oldest invoice, paid or not, so a caller making 5,000 invoices could strand an earlier buyer's payment. `CreatePurchaseInvoice` now refuses past 60 invoices a minute; at 5,000 it makes room only from claimed invoices and from unpaid ones over an hour old that its wallet shows received nothing, and otherwise asks the caller to try later. `expiresAt` was the creation time; it is now 30 days later. `DISK_ALLOCATION_MB` (asked at setup) was never enforced: `CreateDocument` and files received from peers now stop at it, and a document's `size` is the bytes received, not the size the caller claimed. Files a peer pushes without being asked (not a purchase this Hub paid for) are limited to 64 MiB per host and 256 MiB in all per hour. Inventory pages are sized to the frame limit the asking peer announced, so a peer on the 4 KiB legacy limit gets pages it can read. A buyer kept its quote across a seller's resync only when the quoted document came on the first page; a quote now survives the pages of one snapshot (and at most one snapshot that doesn't list the document), so a buyer can pay a quote from before the seller restarted. Asking a seller again replaced the buyer's earlier quote for the same document, so `PayInventoryHtlc { settlementId }` refused a quote the buyer had been given minutes before; the offer now keeps the last four (`earlierQuotes`), each still checked against the listed price and the refund lock. Two quotes for one document at one lock height pay the same HTLC address, so one coin confirmed both settlements and their claims conflicted; a payment already used by another settlement is now refused. A manual `ClaimInventoryHtlcOnChain` that met the Hub's own claim in flight built a second transaction (`replacement-failed`); it now gets the result of the claim in flight. Claims and refunds paid to a new legacy address, whose input can cost more to spend than a sale of a few thousand sats is worth; they now pay to a new Taproot address (segwit when the wallet can't make one).
- **Claims confirm before the refund lock.** A claim paid a flat fee of up to 1,000 sats whatever the fee market, and once broadcast it was never looked at again, so a claim that sat unconfirmed or dropped out of mempools let the buyer refund after the lock and keep the file. The fee now comes from `estimatesmartfee` for a target of a third of the blocks left before the lock (2 to 72), at least 1 sat/vB and at most the sale less dust; without an estimate it stays up to 1,000 sats. Every minute the Hub follows each claim paid to its own wallet until it confirms: it rebroadcasts a claim that left the mempool (or builds it again at the current fee), replaces it with at least twice the fee once a block in the last 12 blocks before the lock, keeps an earlier claim that confirmed over its replacement, and gives the sale up when the buyer's refund took the coin. A claim still being followed is not pruned.
- **Local networks fall back to 1 sat/vB.** `deploy --local` started regtest and signet bitcoind with `-fallbackfee=0.0002` (20 sat/vB), at which a legacy input costs more than most claim coins hold; a Hub with many small sales couldn't send from them. The fallback is now `0.00001`, and regtest no longer raises `-maxtxfee` to 10 BTC.
- **The peering attestation reports the Fabric listener.** `GET /services/peering` and `GetNetworkStatus` read `listening` and the listen address from the HTTP server's agent, which isn't the Hub's Peer and has no `listening` field, so every Hub claimed `listening: false` with no address. Both now read the Peer's socket server.
- **A resold document keeps its price.** When a peer resent its catalog (`fabricResync` on reconnect), the Hub copied each row over its own, so a Hub reselling a bought copy at its own price quoted the seller's price again. A resync now leaves the listing of any document this Hub holds alone.
- **A seller sees a mined payment without txindex.** Confirming an inventory payment asked `getrawtransaction`, which a node without txindex answers only for mempool and wallet transactions, so a buyer's payment mined before the seller confirmed was "not visible". The settlement now keeps its quote height, and confirming looks for the payment in the blocks since then (at most 10,000).
- **Buying a document checks the quote, and an undelivered purchase can be refunded.** A buyer paid whatever address and amount a seller quoted, and had no way back when the file never came. The new admin RPC `PayInventoryHtlc { settlementId | documentId, maxSats? }` pays only a quote whose HTLC address it rebuilds with its own refund key, at the listed price, under `maxSats`, with at least 12 blocks before the refund lock, and keeps the purchase (with its funding transaction) in `bitcoin/inventory-purchases.json`. `RefundInventoryHtlc { settlementId, toAddress?, feeSats? }` spends the refund leaf once the lock height is reached (an HTLC the seller already claimed says so: its claim carries the key), and `ListInventoryPurchases` lists them; a purchase becomes `DELIVERED` when its key arrives. The seller no longer delivers within 6 blocks of the refund lock, where the buyer could take both the file and a refund. `scripts/documents.js buy` pays through it (`--max`, `--lock <blocks>`, `--pay-only`), and adds `refund`, `purchases`, `refresh` (Document Market listings from connected peers), and `publish --id` to re-list a bought copy.
- **Documents bought from another Hub can be opened.** The buyer Hub dropped the seller's `HTLC_KEY_REVEAL` addressed to itself, so a paid inventory purchase left only ciphertext. It now keeps the key when its hash matches the delivered file's `htlcFileV1.paymentHashHex` (a reveal that arrives before the file waits up to 10 minutes), marks the copy sealed under the seller's scheme, and opens it with the new admin RPC `OpenPurchasedDocument { id, preimageHex? }` (the claim witness preimage works too). The seller keeps its HTLC settlements in `bitcoin/inventory-htlc.json`, so a restart between payment and claim no longer loses them; funded settlements that aren't claimed are never pruned; and the funding transaction is saved at confirm time, so a pruned node without txindex can still build the claim. `GetNetworkStatus` adds `fabricIdentityId`, the `id1…` target for `RequestPeerInventory`. `scripts/documents.js` publishes, buys (`--from <seller>`, optional `--via <relay>`), opens, and claims from the command line.
- **A Hub without an operator key keeps its key.** With no `FABRIC_XPRV` / `FABRIC_SEED` / `FABRIC_MNEMONIC` and no unlocked `~/.fabric/wallet.json` (every desktop install by default), the Hub made a new root key on each start: the admin token stopped verifying, and the Hub left every federation it had joined. It now generates the root key once and keeps it as `stores/hub/ROOT_KEY` (`functions/hubRootKey.js`). The desktop shell seals it with Electron `safeStorage` and hands it to the Hub process over the parent port (never through the environment); without OS secure storage, and from the CLI, it is a 0600 file. A key file that can't be read or unsealed stops the start instead of being replaced. Wiping `stores/hub` (`npm run reset:stores`, Admin → Wipe local data) removes it, so the next start is a new identity.
- **Federations: adding a Hub by URL names its federation key.** `ResolveHubIdentity` (Add Hub by URL, `scripts/federation.js` URLs) returned the key that signs the peering attestation, which is the Hub identity key; named federations sign with the cosigner key, so the remote Hub never recognized the invite as its own. The signed PeeringCapability claim now carries `federationPubkey` (null while Federations are off), and `ResolveHubIdentity` returns it as `pubkey` (identity key as `identityPubkey`). A Hub that doesn't publish one is refused with a pointer to add it by key.
- **Hub wallet sends reach the network with transaction relay off.** `-blocksonly=1` makes Bitcoin Core default to `-walletbroadcast=0`, so deposits, Bridge payments, and faucet sends stayed in the wallet and were never broadcast, with no error. Managed nodes now also get `-walletbroadcast=1`, and every Hub wallet send is submitted with `sendrawtransaction` while unconfirmed (covers nodes the Hub doesn't manage); a refused broadcast is reported with the txid.
- **Signing hardening (needs the matching `@fabric/core` and `@fabric/http`):** every Schnorr signature is now a tagged hash for one purpose (`@fabric/core/functions/signingTags`), so a signature made for one purpose can't be replayed as another. Delegation signs under `Fabric/Delegation`, federation invites under `Fabric/FederationInvite`, oracle attestations under `Fabric/OracleAttestation`, and sidechain patch witnesses are checked under `Fabric/SidechainState`. **Device link v3 only:** the Hub browser rebuilds the offer and link strings from the session fields before signing (no more signing a string the server sent), asks before countersigning and shows the other device's key fingerprint, and records only the device it countersigned. **IdentityCrossSign v2:** cross-signs name the device-link session and Hub origin; the cluster links two keys only when both halves name the same session, nonce, and origin, and a revoke removes only its own session's link. The cluster is rebuilt on start from `identity/CROSS-SIGNS`, dropping proofs that no longer verify. `POST /identity/cross-sign` takes only pre-signed proofs. Mesh `CONTRACT_MESSAGE` cross-signs are unwrapped and verified.
